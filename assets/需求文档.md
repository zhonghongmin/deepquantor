## 1. 项目背景与目标

### 1.1 背景

面向 **A 股（个股 + 行业 ETF）** 的量化选股与投资决策支持系统，用一套可复现的量化框架替代主观判断，把「宏观定仓位 → 选行业 → 选个股」做成每天自动跑一遍的固定流程，并让每一步都留下可回溯的依据。

### 1.2 产品目标

**四层大目标**

- **G-A 决策闭环**：宏观、中观、微观三层判断串成一条链路，自动输出「配多少、配什么、买哪些」，人只做取舍、不做重复计算
- **G-B 效果可验证**：任何因子、信号、建议的放行都有 IC/IR、分层回测与胜率回溯支撑，效果可量化、可复现、可对外说明
- **G-C 数据与运营可信**：数据从哪来、何时取的、是否降级全程可查；数据源健康、调度状态、用户权限集中可管
- **G-D 商业化闭环**：前期靠自营实盘验证策略 α，中期免费开放引流，后期以能力开放与会员订阅双轨变现

**三期推进节奏**

| 期      | 大目标                                                      | 服务对象                                        | 商业模式                                                          | 状态   |
| ------ | -------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------- | ---- |
| **前期** | G-1 决策闭环 · G-2 效果可验证 · G-3 数据可信 · G-6 可运营治理 · G-10 自动化交易 | **只服务自己**：内部自营团队，系统不对外开放、不设外部注册入口           | **自营收益**：自动化交易驱动自营资金实盘收益，不依赖外部用户，验证策略 α 与系统稳定性                | 本期交付 |
| **中期** | G-4 内参可跟踪 · G-5 免费吸流与信息整合 · G-8 变现起步                     | **对外引流**：开放外部注册；客户端全量页面与用户账户（SUB-01~06）一并落地 | **免费 + 广告**：信息整合免费开放引流（只展示结论、不泄露策略），外部页面接入合规广告并标注「广告」         | 后续版本 |
| **远期** | G-7 能力可开放 · G-9 多资产扩展 · G-11 大户赋能 B2B                    | **分层开放**：大户 B2B 能力开放，中小户会员订阅                | **双轨变现**：对大户以系统能力赋能（B2B：Open API / 白标 / 私有化）；对中小户收会员费（B2C 订阅） | 另立项  |

### 1.3 本期目标与范围

本期把大目标中的前期部分收敛为**两条独立主线 + 一组契约**：宏观主线出配置比例、**仅作参考**；微观主线独立选股、**不读宏观结论**；中观本期暂缓（D-25）。三条线各自独立产出，只通过冻结的契约在对接层汇合，本期不做联动调优。

- **两条线各自跑通**：宏观一次调度产出 `regime` / `asset_alloc` / `style_tilt`；微观一次调度产出行业准入名单与个股 / ETF 候选清单，互不阻塞
- **效果有据**：因子与信号放行前须有 IC/IR 与分层回测证据，不靠主观判断
- **数据可查**：任一数据项能回答「从哪来、何时取的、是否降级」
- **可运营**：数据源健康、调度状态、用户与权限集中可管
- **服务自己**：本期不对外开放——没有外部注册与客户端入口，使用人只有内部自营团队，权限按角色收敛在管理端
- **可跟踪**：每批结论落档，胜率与超额收益按批回溯
- **可演进**：各层只按契约交付字段；后续要把宏观比例真正约束到配置上，只改对接层，不动宏观判定与微观评分

### 2.2 系统架构与运行形态

```text
调度层   workbuddy 定时任务（cron 语义，避开 9:30–15:00）→ 触发 Python CLI 任务
采集层   Python 采数任务：UnifiedProvider（①星耀 → ②westock → ③akshare → 派生）
计算层   宏观引擎(月频) │ 中观景气轮动(⏸ 暂缓，D-25) │ 微观评分选股(日/周，口径见 §3.1) │ M1 因子实验室 │ 风控总装 │ 回测 │ 跟踪
存储层   PostgreSQL（唯一数据源：行情库 / 因子库 / 信号库 / 组合库 / 计量库 / 任务状态）+ Redis（热点数据与信号缓存）
展示层   Web 站点（Next.js + Tailwind）：本期仅管理端（内部 11 页），只读库，不触发计算
```

> **运行形态**：采集与展示完全解耦，数据库是二者唯一接口。**两条计算主线互不引用**：宏观出配置比例（仅参考）、微观出候选清单（无权重），只在对接层（RK 总装）汇合，契约见 §1.3.1。

| 侧   | 执行方                              | 做什么                      | 不做什么            |
| --- | -------------------------------- | ------------------------ | --------------- |
| 采集侧 | workbuddy 定时任务（cron）→ Python CLI | 采数、宏观与微观计算、风控总装，写库与任务状态表 | —               |
| 展示侧 | 网站（Node.js + Next.js + Tailwind） | 只读库渲染                    | 不采数、不算策略、不做数据兜底 |

三档路由、时点断言、质量校验全部在采集侧完成。技术栈与调度定义见《系统设计总文档》。

**⑤ 边界与异常**

| 场景 | 处理 |
| --- | --- |
| 任务失败 / 部分成功 | 概览页三层卡的「待补」计数与状态标签随之变化；执行明细回任务状态表（`job_instance`），**本页不承接明细**，不做兜底补数 |
| 数据项滞后 / 缺失 | `#monitor` 按状态徽标（ok/warn/bad）逐项标注，不隐藏 |
| 增量下载时官方尚未发布新期次 | 跳过该项并记录原因（「官方尚未发布新一期，当前最新 xx」），**不写空值、不覆盖原值**；状态与期次保持原样 |
| 增量下载部分失败 | 逐项反馈结果（成功 / 跳过 / 失败计数），失败项单独重试，不回滚已完成项 |
| **删除数据项时仍被引用** | **阻止删除**，弹窗列出全部占用方（策略/报表 + 用途）并预告删除代价；数据项与数据均不动（R-AD-9） |
| **删除数据项时历史数据量很大** | 确认框先显示条数再执行；执行中显示「正在清除…」，**不做静默异步**——清除完成前不允许再次点击删除 |
| **删除后发现删错了** | **无回滚**。确认框已明示「历史期次无法回滚」；建议先在运维监控页导出原始数据（确认框内给出该建议文案） |
| **删除数据项后任务变空** | 任务保留并标记「空任务」，在任务列表中可见待处置，**不自动删除**（R-AD-10） |
| **新增数据项未挂载任务** | 「归属任务」列显示「未挂载」，**不得渲染为 `undefined` / 空白 / `—` 混用**；该数据项不参与采集，`已落库 = 0` |
| **数据项改名后删除判定** | 按编码判定，仍能正确识别引用并拒删（R-AD-15）；日志与引用关系**无需人工改动** |
| **区间补跑缺少范围/类型** | 提交按钮置灰 + 字段级错误提示「请填写日期区间与数据类型」，**不发起请求**（R-AD-13 反例） |
| **页面上的权重组合在表中不存在** | 判为配置错误，保存时拒绝并提示「与《数据策略总文档》§1.7 配置表不匹配，请核对象限与货币信用组合」（R-AD-2） |
| 配置保存冲突（并发改同一项） | 以最后写入为准并双留审计 |
| 无权限 | 页面级无权限态（§5.0.1），不展示数据 |

- **数据项表 · 7 列**：`数据项 / 频率 / 库内最新期次 / 官方最新可获取 ⓘ / 待补 / 最近采集时间 / 状态`；「官方最新可获取」列表头带 ⓘ 说明「按官方发布日历推算的最新已发布期次；尚未发布则停留在上一期」

- **为什么用「增量下载」替代原「勾选 + 更新选中」**：
- 原设计让人先勾选要更新的项，但**用户其实不知道哪几项缺**——必须先读表、心算缺口、再勾选，把判断成本推给了人。
- 改为「增量下载全部待补」后：系统自己算出缺口（`待补 > 0` 的项），按钮上直接写明「N 项 / M 期」，一键补齐；**只拉缺失期次**，已落库的期次幂等跳过。
- 勾选机制退出，**避免"只勾了 3 项、剩下 2 项忘了勾"的漏补**，也省掉全选 / 半选 / 重置勾选这一整套控件。
- **交互**：①「刷新元数据」只重查元数据表并刷新「官方最新可获取」列，**不触发采数**（与下载语义严格区分）；②「增量下载全部待补」→ 弹确认框列明「将对 N 项滞后数据发起增量下载，共补 M 期：X（a 期）、Y（b 期）…」，确认后执行；③ 执行中按钮置灰防重复提交；④ 完成后状态条与表格同步刷新，进度区停在终态；⑤ 表格支持按状态筛选、缺失项置顶。
- **状态与异常**：
- 官方尚未发布新期次 → **跳过并记录原因**（「官方尚未发布新一期，当前最新 xx」），**不写空值、不覆盖原值**，期次与状态保持原样；
- 部分失败 → 逐项反馈（成功 / 跳过 / 失败计数），失败项可单独重试，不回滚已完成项；
- 无缺口 → 按钮置灰 + 提示文案，不发起空任务；
- 刷新失败 → 错误态 + 重试入口，不展示兜底值。
- **数据项清单口径**：宏观 **15 项**（国内 8 · 海外 7），逐项清单以《数据策略总文档》§1.2 为准。其中 DR001 为日频项，按 C-12 采集、按 D-18 **仅作辅助信号，不参与周期判定**；外汇储备与欧/日/美宏观两项辅助因子随 **D-31 本期停用、不采集**。**项数待 D-16 确认后可能变为 16 项**（补 DR001）。

> **DR007 不纳入采集（D-14）**：货币价的「价」维只取 `DR001` 绝对水平 + 趋势（不减锚），不设 `dr007` 与 `dr001_dr007_spread_bp` 两列，`classify_money_price` 传入 `dr007` 即抛错。**理由**：DR001 已是货币政策目标利率；DR007 期限价差与银行—非银分层属结构观察，对松 / 紧方向无增量信息，多一项即多一条断链风险。**待确认（D-16）**：清单未单列 DR001，建议补入成 16 项。
>
> **宽货币只由「量」判定（D-18）**：`factors.money` 仅由货币量（M2 同比、M1−M2 剪刀差）决定；DR001 不进入 `factors.money` / `money_s` / `money_credit` / `regime` / `phase` / `equity_weight` / `style_tilt` / `confidence` 任一周期输出，也不触发 `confidence_delta`。DR001 仍日频采集落库（C-12）；`warn_flags` 落库与日频预警展示随 D-30 后移。**理由**：周期判定是月 / 季频状态机，日频扰动（税期、季末、缴准、政府债缴款）会把资金面噪音误读为政策转向，破坏「同输入同输出」。

- **新增 / 编辑数据项 · 弹窗表单**：数据项名、字段名、频率、**因子层级 ***、数据源接口、公布时间、归属任务；数据项名为空或重复时阻止保存
- **筛选条（定时任务） · 发布机构下拉**：「同机构同时点发布的数据项归为一个任务」——这是任务的划分原则，页面显式声明
- **定时任务表 · 列**：`任务 / 发布机构 / 覆盖数据项 / 执行时点 / 下次执行 / 最近执行 / 操作`；操作为 `编辑` / `删除` / `立即执行`；「覆盖数据项」由数据项挂载关系聚合，**不可在任务侧直接改挂载**（改挂载在数据项编辑弹窗的「归属定时任务」下拉）
- **定时任务补充能力 · 启停 / 补跑 / 执行历史**：① `启用 / 停用` 开关（对应 workbuddy 定时任务启停，双写）；② `按区间补跑`：弹窗必填「日期区间 + 数据类型」，**三者缺一不可提交**；③ `执行历史`：按任务筛选的实例列表，字段为触发方式（自动 / 手动 / 补跑）、起止时间、耗时、退出码、状态、重试次数、操作人；日志详情跳平台原生页（内网代理）
- **删除数据项弹窗 · 引用检查 + 删除范围（核心）**：见下方「删除数据项规则」
- **删除任务弹窗 · 二次确认**：列出任务名与覆盖数据项数；**任务被删不影响数据项本身**（数据项转为「未挂载」，归属显示 `—`）

- **删除数据项规则**：DL-07 / DL-08，不可逆操作，本页最关键的行为约束。

删除一个数据项 = 删除它的配置 + **它的全部历史数据 + 它的运行日志**。因此必须分两条分支处理，**顺序不能颠倒**：

**分支 A｜先查引用，有引用即拒绝**

1. 点删除后先查引用关系表（《数据策略总文档》§4.5 `dataRefs`），不直接弹确认框。
2. 被任一策略或报表引用 → 弹「**无法删除：数据项仍被引用**」：
   - 说明后果：「X」正被 N 个使用方引用，直接删除会导致其运行失败或结果失真；
   - 逐条列出占用方（名称 + `策略` / `报表` 标签 + 用途）；
   - 给出解法路径：先到「策略与因子」页解除引用，再删除；
   - 预告删除代价（历史数据 N 条、相关日志 M 条将一并清除）；
   - 弹窗只有「我知道了」一个按钮，不提供「仍然删除」。
3. 被拒绝时数据项与其数据一律不动（有测试断言）。

**分支 B｜无引用，二次确认后彻底删除** 1. 弹「**删除数据项及其数据**」确认框，**先列删除范围再让人点确认**：

| 行 | 内容 | 说明文案要求 |
| --- | --- | --- |
| 历史数据 | N 条（红字） | 「库内全部期次（最新期次 及以前）」 |
| 运行日志 | M 条（红字） | 「仅该数据项相关记录，其他任务日志不受影响」 |
| 采集任务 | 任务名 / 「未挂载」 | 「任务本身保留，仅移除该项，其余数据项继续采集」 |

1. 加粗提示：「删除后该项不再采集，历史期次无法回滚。建议先确认下游无其他系统依赖此数据。如需保留原始数据用于审计，请先在运维监控页导出。」
2. 确认按钮文案为「**确认删除并清除数据**」（明确表达不可逆），而非泛泛的「确定」。
3. 执行顺序（必须按此序，任一步失败即中止并提示）：① 清空历史数据（`rows` → 0、`latest` → `—`、`gap` → 0）→ ② 移除该数据项相关的运行日志 → ③ 兜底清理引用关系表中的残留行 → ④ 从数据项列表移除。
4. 完成后 toast 回报实际清除量：「已删除「X」，并清除历史数据 N 条、运行日志 M 条。」
5. **跨页联动**：概览页 L1 卡片的数据项数、库内总记录数、监控页表格行数**同步刷新**（有测试断言）。

- **交互**：① 数据项 Tab 的筛选与关键词即时生效，「共 N 项」实时反映结果；② 编辑弹窗标题带数据项名，保存后行内即时更新；③ 「立即执行」经 workbuddy 定时任务触发并回显批次号，执行结果去 `#overview` 运行日志看（本页不嵌日志）；④ 删除任务走二次确认，删后归属列显示「**未挂载**」，不触发数据删除（删任务 ≠ 删数据）；⑤ 改 cron 只在保存时校验一次（服务端二次校验交易时段），保存即写平台并回显新的「下次执行」。
- **状态与异常**：
- 空态：筛选无结果时显示「当前筛选下没有数据项」，**中观层筛选额外提示「（中观层尚未接入数据）」**；
- 字段缺失：新增/编辑时未填因子层级 → 行内错误提示，不落库；
- 名称冲突：新增的数据项名与已有项重名 → 阻止保存并提示重名；名称全库唯一，编码由系统生成且不可改（见《数据策略总文档》§4.5 ⑥）；
- 未挂载：新增数据项未选任务 → 该行「归属任务」显示「未挂载」，**不得渲染为 `undefined` 或空白**；
- 权限：删除与编辑限管理员 / 运营，研究员只读（无操作列，见 AD-07）；
- 全部落审计：新增 / 编辑 / 删除 / 删除连带清除的数据量，均写 `platform.audit_log`（AD-07）。

### 5.10 FR-10 调度与编排（SC）

> 来源：**《数据策略总文档》§3（调度规则）**、**《数据策略总文档》§1.10 再平衡与触发**。调度由 **workbuddy 定时任务**触发 Python CLI，任务状态写库供网站展示（§2.2）。

#### 5.10.1 业务逻辑（功能视角 · 引用式）

**① 功能职责**

- 把「采数 → 宏观与微观计算 → 总装 → 落库」串成一次**可重复执行的批次**；任务以 CLI 形态提供，由 workbuddy 定时任务按 cron 触发。
- 负责依赖编排、重试、幂等与**任务状态写库**（网站据此展示运行状态）。

**② 任务状态机（编排层职责）**

```text
pending（等待触发）→ running（CLI 执行中）→ success
                              ├─> partial（部分成功：非关键项失败）
                              └─> failed（关键路径失败）
上游 failed/partial → 下游 skipped（状态与原因写入任务状态表）
failed / partial → 指数退避重试（N 次可配）→ 仍失败 → 告警
```

**③ 权威引用（时点与频率以被引用文档为准，本文档不重复时间表）**

| 内容 | 权威出处 | 本文档怎么用 |
| --- | --- | --- |
| 任务入口与 CLI 执行形态 | 《系统设计总文档》 | C-10 / SC-01 引用，不内联选型 |
| 抓取调度窗口与默认时点（默认 02:00）、禁止交易时段 | 《数据策略总文档》§3 调度规则 | C-1 / SC-02 / SC-06 校验规则 |
| 各层运行频率（宏观月频 / 中观月·季 / 微观日·周 / 跟踪日） | 《数据策略总文档》§4.3 频率与再平衡、§2.5 | SC-01 只写「按层定义频率编排」 |
| 再平衡与触发条件 | 《数据策略总文档》§1.10 | BT-04 引用 |
| 持仓盯市时点 | 《数据策略总文档》§3.6 R-PT-4 | PT-04 |

**④ 边界与异常**

- 交易时段启动 → 拒绝并告警（单测）；取数后最新交易日不符 → 重试 N 次后告警（SC-03）。
- 同日重跑 → 幂等，结果一致无重复记录（SC-05）。

| **PT 投资跟踪与组合管理** | **真实/模拟持仓与资金** | 持仓口径：成交价、费用、仓位、市值、浮盈，与基准/回测对照 | 组合账本、盯市、再平衡与风控提示 | 内部（自营/模拟盘） |
| **IN 内参与效果跟踪**（中期） | 对外发布的**内参内容** | 不独立计算，取 TK 结果脱敏投影 | 内参文章 + 对外效果公示页 | 外部用户（中期客户端 CL） |

- **单一数据源**：效果/胜率口径**唯一由 TK 产出**；本期只在管理端 `#research` 内部消费，中期对外公示（CL-03，后续内参重启后为 IN-03）只做展示与脱敏，**禁止另算一套命中率**；PT-07「实盘 vs 回测差异」引用 BT 结果。
- **区别示例**：同一只股票——TK 记"信号发出后 T+5 涨 8%"（未买入也统计）；PT 记"实买 1 万元、费用 5 元、浮盈 800"（未买入则不存在）；IN 展示"上周内参提及、命中率 62%"（数据取自 TK）。
- **不合并的理由**：TK 评估"算法准不准"（全样本信号），PT 管"钱怎么变"（仅实际持仓），IN 管"对外说什么"（脱敏内容）。合并会导致信号样本缺失或对外口径失真。

### 8.2 反例要求

每条规则须有**反例测试**：极端态（滞胀 + 双紧）仓位上限、涨停 / 停牌不可成交、数据未更新触发重试、未挂载任务的数据项参与采集。付费墙类反例随中期客户端立项时补。

- **通用**
    - 极端态（滞胀 + 双紧）超仓位上限
    - 涨停 / 停牌仍成交
    - 数据未更新未重试
    - 未挂载任务的数据项被计入采集
- **宏观判定（D-24）**
    - `money_credit=双宽` 且增长收缩时 `regime` 非「衰退」、`equity_weight_base ≠ 62.5%`，或未降 `confidence`（MC-02 / MC-07）
    - 九宫格内出现周期名
    - 未来数据回写 `macro_signal`
    - 命中率无基准、样本外未通过却升级「领先性」（MC-08）
    - `regime` 出现第五状态；36 格表非 36 行；命中外二次折减；两层数据所属期不一致仍出 36 格（T-8）
- **微观隔离（D-25）**
    - MicroSignal 含 `weight` / 目标占比
    - 读取 `style_tilt` / `equity_weight` / `asset_alloc` / meso Top-N
    - 写入 `macro_signal` 或改 `confidence`
    - 中观暂缓期出现 MD 代码与测试，或伪造行业超配清单
    - 中观任务缺失时微观报错中断（应 skipped 且照常出批次）
    - 全维缺失仍出建议，或降级项补零 / 前值填充
    - `#micro` 出现宏观主判 / `asset_alloc` / `equity_weight`
- **选股域与行业评分（D-26）**
    - 全市场直选（`universe_mode` 应为 `industry_first`）
    - 行业评分输出 `overweight` / `weight` / 金额
    - 指数成分取到 `as_of` 之后的批次
    - 宏观快照前后不一致，或 `job-meso` 非 `skipped`
- **微观页口径（D-27）**
    - PB / PE / PS 原始值直接跨行业排序
    - `#micro` 出现六维权重卡 / 有效性回溯区
    - 四条件筛选回写并改变准入名单
    - 行业明细含 `weight` / 目标占比 / 超配比例
    - 10 日走势取到 `as_of` 之后，或负 PE 未剔除 / 缺失补零
